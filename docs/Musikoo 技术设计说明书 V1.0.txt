## 1. 文档概述

本文档旨在详细定义 Musikoo 平台的技术实现方案。它基于商业计划书 V6.0 的产品愿景，将“乐句级音乐素材库与哼唱搜索引擎”的所有功能转化为具体的工程语言，包括数据模型、接口逻辑、关键算法流程、存储方案以及非功能性需求。

**核心目标：**
- 实现公版古典音乐的乐句级结构化拆分、多维标签标注与高品质音频渲染。
- 构建支持哼唱（音频输入）、帕森斯轮廓码、首调简谱、独立节奏的混合检索系统。
- 保障数据的版权安全、防爬机制与一致性。
- 提供可扩展的架构，支持未来向流行音乐、民歌等类型的扩展。

## 3. 核心数据模型

### 3.1 域模型解耦设计

遵循“作品-乐谱版本-录音版本”三域分离原则，乐句结构锚定于乐谱版本。

```
Work (作品)
 ├── WorkMeta: 标题, 作曲家, 年代, 风格, 作品号, 所属剧名...
 ├── Score (乐谱版本) 1
 │    ├── Movement (乐章)
 │    │    └── Phrase (乐句) ← 所有检索向量和标签的核心载体
 │    └── ...
 ├── Score (乐谱版本) 2
 └── Recording (录音版本) * (未来扩展)
```

## 4. 功能模块与解决方案

### 4.1 乐句结构化生产管道 (The Distiller)

#### 4.1.1 上传与解析
- 支持上传 `.musicxml`、`.mxl` 文件。
- 后端使用 Python `music21` 解析，校验格式、提取基本元数据（拍号、调号、声部数量等）。
- 自动剥离无关声部，聚焦主旋律声部（可人工调整）。

#### 4.1.2 自动乐句预切 (AI Cold Start)
- **规则基础**：基于休止符、长音、终止式（V-I进行）进行初步乐句边界检测。
- **机器学习增强**：使用序列标注模型（如基于BiLSTM+CRF）对旋律的音符进行“分句边界”分类，模型训练数据来源于历史人工标注。
- **输出**：为每个乐章输出一组建议的乐句起止小节/拍。

#### 4.1.3 Web端人工精标工具 (The Distiller UI)

**界面布局与交互流程**
- **左右分屏**：左侧为完整 OSMD 乐谱，右侧为选中乐句的展示与试听面板。
- **乐句边界调整**：标注员可拖拽预切边界，或直接在五线谱上框选音符段落生成新乐句。

**风格感知的单旋律蒸馏（核心升级）**
面对轮指、装饰音群等高辨识度但难以逐个哼唱的音型，蒸馏工具不再仅提供“骨干化”一刀切模式，而是引入**风格感知的双轨蒸馏机制**。

1. **点选主旋律骨架**  
   标注员用鼠标在乐谱上点选属于“核心旋律线”的音符。对于普通旋律直接点击；对于风格性短音群（如《爱的罗曼史》中吉他轮指高音、《钟》的重复跳跃音型），使用**“风格性音群标记”画笔**框选该组音符，右键标记为以下类型之一：
   - `tremolo`（轮指/震音）
   - `grace_note_cluster`（装饰音簇）
   - `wide_leap_ostinato`（大跳固定音型）
   - `rapid_repeated_notes`（快速同音反复）
   - `trill`（颤音）

2. **双轨旋律自动生成**  
   系统根据标记自动生成两套旋律表示：
   - **展示轨 (`solfege_melody_display`)**：完整保留标记内的所有音符，仅作首调归一化，用于音频渲染和乐谱展示，确保听众获得原汁原味的风格。
   - **检索轨 (`solfege_melody_search`)**：对标记的音群进行“智能合并”：将一串轮指或装饰音群聚合为一个与该音群总时值相当的骨干音（取音群起始音高或平均音高），并保留合并后的时值。单个标志性装饰音（如《特里斯坦和弦》前的倚音）可由标注员手动点击提升为骨干成员，不被合并。

3. **风格模式标签 (`stylistic_pattern`)**  
   框选的音群会直接导致该乐句的 `stylistic_pattern` 字段被填充对应枚举值。若乐句无此类特征，字段为 `NULL`。该标签将在检索时显著影响权重分配。

**特征标记与提交**
- 对当前乐句勾选 `is_eye_1/2/3`、`is_heart`、`position_type`。
- 添加情绪/场合标签。
- 提交时前端发送：原始音符序列、标记的音群区域、人工标签。
- 后端校验：即时生成 `solfege_melody_display`、`solfege_melody_search`、`rhythm_vector`、`parsons_code`，并强制检查 `len(solfege_melody_search) == len(rhythm_vector)`，失败即拒绝并提示修正。

#### 4.1.4 众包标记机制
- 登录用户可在乐句详情页提交边界微调或标签建议。
- 建议存入审核队列，由专家审核后版本化更新，贡献者获积分。

### 4.2 特征提取与转换算法

所有算法通过离线管道（Python）执行，并在人工标注后重新触发。本节重点描述新增和调整的部分。

#### 4.2.1 双轨首调简谱生成
- **展示轨生成**  
  对标注员点选或保留的所有音符（含风格性音群内全部音符）进行首调转换，规则同原方案：识别片段调性，将绝对音高转为音级数字+升降+八度标记，形成 `solfege_melody_display`。
- **检索轨生成**  
  先应用“风格感知骨干化”规则：将标记为风格性音群的音符序列替换为聚合骨干音（时值 = 音群总时值，音高 = 音群起始音或平均音高，取整）。其余旋律不变。再对骨干化后的序列进行首调转换，生成 `solfege_melody_search`。

#### 4.2.2 归一化节奏向量 (`rhythm_vector`) 生成
- 输入为**原始完整音符序列**（含标记音群内的每个短音），量化时值单位 `L:1/16`。休止符编码为 `0`。
- **关键点**：即使检索轨旋律被骨干化，节奏向量仍保留完整的颗粒度，例如轮指段会生成一串密集的 `1 1 1 1...`，这成为辨识风格的核心特征。

#### 4.2.3 帕森斯轮廓码 (`parsons_code`) 生成
- **粗粒度处理**：对标记为风格性音群的段落，系统先将其内部所有音符视为一个整体，比较该音群整体与前后的音高关系，生成一个粗略的方向符（`U`/`D`/`R`），以避免密集短音造成轮廓跳变噪音。
- 其余普通音符按常规逐对比较生成 `U/D/R` 序列。
- 最终拼接为完整的 `parsons_code`。

#### 4.2.4 Eye/Heart 自动预标注算法（不变）

#### 4.2.5 风格模式标签 (`stylistic_pattern`) 生成规则
- 由标注员通过 UI 标记后直接写入。
- 自动辅助检测：后端可预扫描乐谱，对连续4个以上十六分音符的同音反复或大跳给出 `tremolo` 或 `wide_leap_ostinato` 的候选建议，标注员确认后生效。

### 4.3 检索引擎：混合多维匹配

#### 4.3.1 索引构建
- `phrases` 表的 `solfege_melody_search`、`rhythm_vector`、`parsons_code` 及 `stylistic_pattern` 在创建/更新时同步至内存搜索引擎（如 Elasticsearch 结合向量插件）。
- `solfege_melody_display` 仅存储不索引，用于展示和渲染。

#### 4.3.2 哼唱搜索接口 (`/api/search/hum`)

**输入**：用户哼唱音频（10–15 秒 WAV）。

**处理流程**：
1. **基频提取**：使用 `librosa` 或 `pYIN` 提取音高轨迹，转为MIDI序列。
2. **量化分割**：切分为音符事件，量化时值。
3. **生成查询向量**：
   - `Q_parsons`：对提取的旋律计算帕森斯轮廓码（应用与索引一致的粗粒度规则）。
   - `Q_solfege`：将提取旋律转为首调简谱（需自动估计主音或利用用户交互）。
   - `Q_rhythm`：计算归一化节奏向量。
4. **三级漏斗检索**：
   - **粗筛**：用 `Q_parsons` 与 `parsons_code` 进行编辑距离/DTW匹配，选出Top K候选（K=200）。
   - **精排**：对候选集分别计算：
     - `score_solfege = sequence_similarity(Q_solfege, doc.solfege_melody_search)`
     - `score_rhythm = sequence_similarity(Q_rhythm, doc.rhythm_vector)`
   - **风格感知动态融合**：
     - 计算查询音频的节奏复杂度（如时值熵）和音高稳定性（音高方差倒数）。
     - 若 `doc.stylistic_pattern` 非空，且查询音频呈现高节奏复杂度、低音高稳定度，则大幅提升 `w_rhythm` 权重（如至 0.8），同时给予该文档额外加分（+boost）。
     - 其余情况默认 `w_solfege=0.6, w_rhythm=0.4`。
     - 最终得分：`final_score = w_solfege * score_solfege + w_rhythm * score_rhythm + style_boost`。
5. **返回结果**：得分最高的前20条 `Phrase` 记录，包含试听音频、作品信息、标签及Eye/Heart标识。

#### 4.3.3 文本/代码搜索接口 (`/api/search/text`)
- 支持直接输入帕森斯代码、简谱数字串、节奏型字符串进行检索。
- 对于简谱输入，可指定查询目标调性，或由系统自动转换后与 `solfege_melody_search` 匹配。
- 风格标签可作为筛选条件（如筛选 `stylistic_pattern = tremolo`）或提升排序权重。

#### 4.3.4 标签过滤与全文搜索
- `emotion_tags`、`occasion_tags`、`prominent_instruments`、`stylistic_pattern` 等字段同步至 Elasticsearch，支持组合条件过滤与多维度混合查询。---

### 4.4 音频渲染与分发

#### 4.4.1 乐句音频合成管道
- **输入**：某个 `phrase` 的 `musicxml_snippet_url` 和该声部配置。
- **渲染**：使用预先部署的虚拟乐器音源（通过 MIDI 触发）。可选择标准 General MIDI 用于低品质方案，或使用 SFZ/Spitfire 音源产生高品质WAV。
- **自动化**：后端部署渲染服务（Python `midi2audio` 或自定义 FluidSynth 服务），接收乐句XML并返回音频文件。
- **存储**：
    - 低码率 MP3（128kbps）带有轻微水印（元数据中标记 Musikoo），用于公开试听。
    - 高码率 WAV（48kHz/24bit）无水印，存放于受权限控制的 OSS Bucket，仅订阅用户可生成临时下载URL。

#### 4.4.2 精确定位播放
- Web前端加载完整 MusicXML，根据 `phrase.start_measure` 和 `start_beat` 计算 OSMD 的光标 Tick 位置，实现一键跳转并仅高亮播放该乐句段落。播放时采用 `Tone.js` 或 OSMD 内置播放（默认MIDI），可选切换渲染音频。

### 4.5 数据安全与反爬策略

- **接口保护**：所有资源ID使用UUID，杜绝遍历。未经登录的IP实施严格的API频率限制。
- **按需加载**：前端不直接返回 `solfege_melody`、`musicxml_snippet_url` 等核心数据，仅在用户触发播放或查看详情时，通过一次性 Token 获取。
- **数据埋雷**：在 `start_beat` 等数字字段中故意插入肉眼不可见的浮点偏移（如 `2.00001`），在 `abc_search` 尾部插入零宽字符。若第三方数据出现相同特征，即可作为侵权证据。
- **乐谱版本水印**：所有公开 MusicXML 下载文件内嵌不可见元数据，关联请求者ID。

### 4.6 用户系统与社区功能

- **用户账户**：支持邮箱注册、OAuth登录。角色分为普通用户、标注员、管理员。
- **用户榜单**：
    - 用户可对作品或乐句进行投票（赞/踩），系统计算热榜、趋势榜。
    - 用户可创建自定义收藏集（Playlist of Phrases），设为公开或私密。
    - 后端实现收藏集表：`collections`, `collection_phrases`。
- **数据贡献追踪**：记录用户标注、纠正的贡献量，用于积分和排名。

## 5. 非功能性需求

- **响应时间**：哼唱搜索请求在5秒内返回结果；文本搜索在1秒内。
- **吞吐量**：支持初期1000 QPS的检索请求，架构可水平扩展。
- **数据一致性**：任何对 `phrases` 核心向量的修改必须满足事务原子性，并记录版本历史。
- **可扩展性**：乐句数据模型中的标签字段设计为JSON，方便未来增加新的标签维度，无需改动表结构核心。
- **版权合规**：渲染音频的权利声明完全基于公版乐谱和自有合成，杜绝任何第三方录音版权风险。平台需在显著位置提供可商用授权说明。

## 6. 部署与DevOps

- **CI/CD**：GitHub Actions 实现前后端容器化构建，部署至 AWS ECS 或阿里云 ACK。
- **环境分离**：开发、预发、生产环境隔离。脱敏后的数据用于测试。
- **监控与日志**：使用 Prometheus + Grafana 监控服务健康度，ELK 或 Loki 收集日志并告警。
